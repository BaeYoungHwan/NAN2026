## 1. 확정해야 할 값 (5개)

전부 `src/core/tuning.ts`의 `TUNING_DEFAULTS`에 있다.

| # | 파라미터 | 현재값 | 무엇이 걸려 있나 |
|---|---|---|---|
| 1 | `shadowLength` | 80px | 그림자가 화면에서 차지하는 길이. 1R 가이드 부채꼴 반지름(`shadowLength + 20`)도 같이 변한다 |
| 2 | `safeAngleTolerance` | ±30° | 난이도의 핵심. 좁히면 전 구간이 어려워지고, 3R은 여기에 배율 0.5가 또 곱해진다 |
| 3 | `rotationSpeed` | 180°/초 | 안전 구역이 움직이는 속도를 따라잡을 수 있느냐를 결정 |
| 4 | `round3ToleranceMultiplier` | 0.5 | 3R 디메리트 강도 |
| 5 | `lightSpacingSteps` | 8 | 가로등 간격. 넓히면 광원 전환이 줄어 쉬워지고, 좁히면 전환이 잦아 어려워진다 |

**함께 봐야 하는 값**: `lightSwitchGraceSeconds`(1.2초)는 2·3번에 종속된다 — 유예 시간의 근거가 "180° 회전에 걸리는 시간(π/rotationSpeed ≈ 1초) + 여유"이므로, `rotationSpeed`를 바꾸면 이 값도 다시 계산해야 한다.

**건드리지 않는 값**: `corridorWidth`(2), `savePointsPerStage`(1)은 확정 완료. `worldCols`/`worldRows`(20×15)는 바꾸면 세 스테이지 지형이 전부 달라지므로, 이번 제출 범위에서는 손대지 않는다.

## 2. 진행 방법

### 준비

- 조정용: 개발 서버 + `?tune=1` (슬라이더 실시간 조정, 라운드별 경과 시간·사망 횟수 자동 계측, 확정용 diff 출력)
- 체감 확인용: **`?tune=1` 없는 빌드**. 패널을 띄운 채로 난이도를 판단하면 안 된다 — 값이 보이는 상태의 플레이는 심사자의 플레이와 다르다
- 참가: 최소 3인(팀 2인 + 외부 1인 이상). **외부 1인의 첫 플레이가 가장 중요한 데이터다** — 팀원은 이미 정답 경로를 알고 있어 난이도를 낮게 느낀다

### 순서

1. **1라운드: 손대지 말고 현재값 그대로 3인 플레이** → 기준선 확보. 여기서 나온 숫자가 없으면 조정이 감(感)이 된다
2. **2라운드: 기준선에서 가장 크게 어긋난 항목 하나만** 조정 → 재플레이. 한 번에 두 개 이상 바꾸면 어느 것이 효과였는지 알 수 없다
3. 목표 범위(§3)에 들어오면 확정, 아니면 2를 반복

### 기록 양식 (플레이어 1인당 1행)

| 플레이어 | 1R 시간 | 1R 사망 | 2R 시간 | 2R 사망 | 3R 시간 | 3R 사망 | 완주? | 포기 지점 | 한 줄 소감 |
|---|---|---|---|---|---|---|---|---|---|
| | | | | | | | | | |

## 3. 판정 기준

### KPI 대조 — 실측이 먼저다

PRD의 KPI는 클리어율 40~60%, 평균 플레이타임 10분이다. 그런데 **무사망 자동 조종 실측 총 플레이 타임은 53초**였다(1R 19.4초 + 2R 22.1초 + 3R 12.0초).

사람이 죽어가며 하면 이보다 훨씬 길겠지만, 10분에 맞추려고 난이도를 억지로 올리는 것은 순서가 뒤바뀐 것이다. **실측이 KPI에 못 미치면 KPI 쪽을 실측에 맞춰 하향 수정한다** — 심사 문서에 적힌 목표와 실제 게임이 다른 편이 훨씬 나쁘다.

### 3R 난이도 — 이번 테스트의 핵심 판정 항목

헤드리스 실측에서 확인된 것: **3R에서 이동을 멈추지 않으면, 광원 근접 구간(최소거리 ~40px)에서 자연각 변화 속도가 회전 속도(180°/초)를 순간적으로 초과해 통과가 거의 불가능하다.** "멈춰서 재정렬 → 전진"이 사실상 강제된다.

판정 갈래는 셋이다.

| 판정 | 조치 |
|---|---|
| 의도된 난이도다 (멈춤-전진이 이 게임의 리듬) | 값 그대로 확정. **튜토리얼 대사에 "위험하면 멈춰서 각도부터 맞추라"는 안내를 한 줄 넣는다** — 몰라서 죽는 것과 알고도 못하는 것은 다르다 |
| 너무 어렵다 | `round3ToleranceMultiplier`를 0.5 → 0.6~0.7로 완화 (3R만 영향, 1R·2R 불변이라 부작용이 가장 작다) |
| 광원 근접이 문제다 | `lightSpacingSteps`를 넓혀 광원 밀도를 낮춘다 (전 라운드에 영향 — 마지막 수단) |

### 그 밖의 기준

- **외부 참가자가 1R을 튜토리얼 대사만 읽고 클리어**하지 못하면 → 온보딩 문제다. 값이 아니라 안내를 고친다
- **2R에서 "가이드가 없어져 뭘 해야 할지 모르겠다"**가 나오면 → `safeAngleTolerance`를 넓히는 게 아니라, 그림자 색상 피드백·경고음이 제 역할을 하는지 먼저 본다
- **아무도 안 죽으면** 너무 쉬운 것이다 — 사망 0인 완주는 심사에서 "쉬운 게임"으로 읽힌다

## 4. 확정 후 반영할 곳 (3곳 + 1)

값을 정하고 나면 반드시 네 곳을 함께 고친다. 하나라도 빠지면 코드와 문서가 어긋난다.

1. **`src/core/tuning.ts`** — `TUNING_DEFAULTS` 값 + 파일 상단 "확정 상태" 표의 `임시` 표기를 지우고 근거 한 줄 기재
2. **`docs/product-specs/PRD-v1.md` §12** — 미결 사항 표를 확정 내용으로 갱신 (KPI를 하향했다면 그 절도 함께)
3. **해당 ADR** — 그림자·각도는 ADR-002, 통로·생성은 ADR-003, 광원 간격은 ADR-004
4. **재배포 + 스크린샷 재촬영** — `safeAngleTolerance`가 바뀌면 1R 가이드 부채꼴 크기가 달라지므로 `docs/submission/screenshots/03-round1-guide.png`를 다시 찍고 `node scripts/optimize-screenshots.mjs` → `node scripts/build-submission-pdf.mjs`
