# ADR-003: 스테이지 절차적 생성 — 타일 그리드 + Carve, 판정자 주입 충돌

> 상태: Accepted
> 날짜: 2026-07-23
> 결정자: 배영환

## 컨텍스트

지금까지는 정적 스테이지 1개(하드코딩 광원·스폰)만 있었고, 캐릭터는 캔버스 사각형 경계로만 clamp되며 벽/통로가 없었다. 원래 기획 한 줄 소개("좁은 통로를 탈출")에 맞춰 절차적 생성 범위에 벽/통로를 포함하기로 했고, 통로가 생기면서 "출구 도달 = 클리어" 조건도 필요해졌다.

송원호님의 맵 디자인 작업은 현재 스타일/컨셉 참고용이고 실사용 에셋은 미정이라, 절차적 생성은 시각 에셋과 무관하게 순수 데이터(그리드) 레벨로 설계하고 렌더링은 기본 도형으로 그린 뒤 나중에 아트로 교체 가능하게 분리해야 한다.

핵심 제약: 그림자 각도 판정(`shadow/`, ADR-002)은 이 작업으로 전혀 변경하지 않는다 — 벽/통로는 캐릭터의 물리적 이동에만 관여하고 "그림자 각도가 안전 구역 안인가" 판정과는 완전히 무관하다.

## 결정

지형을 **타일 그리드**(`TileGrid`, 0=walkable/1=wall)로 표현하고, **시드 기반 random-walk carve**로 통로를 생성한다. 벽-캐릭터 충돌은 `physics`에 **충돌 판정자(predicate) 주입** 방식으로 추가하고, 캐릭터 이동은 **축 분리(X→Y)** 로 처리한다.

**선택: 타일 그리드 + Carve + 판정자 주입 + 축 분리 이동**

## 고려한 대안

| 옵션 | 장점 | 단점 | 탈락 이유 |
|------|------|------|-----------|
| 타일 그리드 (채택) | 충돌판정이 셀 조회로 O(1), 렌더도 셀당 사각형으로 자명 | 해상도가 타일 크기로 제한됨 | 800×600/40px 규모에서 무의미한 단점 |
| 선분/사각형 리스트 | 임의 형태 표현 가능 | 원-사각형 겹침 판정이 모서리에서 미묘해 디버깅 비용 높음 | 18일 일정에 과함 |
| 단순 random-walk (미방문 셀 우선 없음) | 구현 최소 | **실제로 시도했다가 실패**: 이미 지나온 셀을 피하지 않아 통로가 좁은 구역 안에서 스스로 겹치며 맴돌아 스폰-골 거리가 거의 0이 됨(브라우저 실측으로 발견) | 미방문 우선 + 직진 가중치(0.75) + 최소 거리 미달 시 재시도로 교체 |
| 정교한 던전 생성기(BSP 등) | 결과 품질 높음 | 18일 일정에 과함, 디버깅 어려움 | 요건(빠르고 예측 가능) 미충족 |
| 충돌판정을 그리드에 직접 결합 | 구현 약간 단순 | `physics`가 그리드 표현에 종속돼 테스트·표현 교체가 어려워짐 | 판정자 주입으로 결합도 낮춤 |

## 결과

**긍정적 결과:**
- `generateStage(seed)`가 결정론적(같은 시드 = 같은 스테이지)이라 디버깅·테스트가 쉬움
- `createGridCollider`가 판정자만 반환해 `physics/character.ts`가 그리드 표현을 몰라도 됨 — 테스트에서 trivial predicate 사용 가능
- `drawStage(ctx, stage)`로 렌더링이 분리돼 있어, 실제 아트가 나오면 이 함수만 교체하면 됨

**부정적 결과 / 트레이드오프:**
- 초기 구현(미방문 셀 우선 없이 역주행만 금지)은 스폰-골 거리가 거의 0에 가까운 뭉친 통로를 만드는 버그가 있었음 — 브라우저 실측(캐릭터가 몇 걸음 못 가고 멈춤)으로 발견 후 미방문 우선+직진 가중치+최소거리 재시도로 수정
- 통로 폭(2셀)·경로 길이(40스텝)·최소 스폰-골 거리(10셀) 모두 임시값 — 플레이테스트로 튜닝 필요 (PRD §12)

**위험 요소:**
- 통로가 너무 좁으면(캐릭터 반지름 대비) 이동이 답답하게 느껴질 수 있음 — 완화: 통로 폭을 플레이테스트 1순위 튜닝 대상으로 명시

## 구현 시 주의사항

- carve 알고리즘은 반드시 "미방문 셀 우선" 규칙을 유지한다 — 이게 없으면 통로가 스스로 겹치며 뭉친다(실제로 겪은 버그)
- `moveCharacter`의 축 분리(X 먼저, Y 다음) 순서를 바꾸지 않는다 — 대각선 이동 시 벽을 따라 미끄러지는 조작감이 이 순서에 의존함
- 그리드 크기(20×15, 타일 40px)는 캔버스(800×600)와 반드시 일치해야 한다 — `CANVAS_WIDTH`/`CANVAS_HEIGHT`는 `procgen/stageGenerator.ts`에서 export하는 값을 유일한 소스로 사용한다

## 재검토 조건

- 여러 스테이지 연속 진행(클리어 후 다음 스테이지 전환) 구현 시 시드 관리 전략 재검토 필요
- 라운드 시스템(1R~3R)이 스테이지 재생성과 연동되어야 한다면(예: 라운드마다 새 시드) 이 ADR의 "단일 스테이지" 가정 재검토 필요
- 장애물의 그림자 occlusion을 추가하게 되면 grid와 shadow 도메인 간 새로운 연동 지점이 필요함

## 재검토 조건 해소 기록 (2026-07-28)

위 두 조건이 실제로 트리거되어 "단일 스테이지" 가정을 폐기했다 — `Stage`는 이제 "한 라운드 전체"를 의미하고, 라운드 전환은 곧 새 `Stage` 생성이다.

- **시드 관리**: `procgen/stageGenerator.ts`에 `seedForRound(baseSeed, round)` 추가. 내부 재시도용 `deriveSeed`와는 별도의 변환(`deriveRoundSeed`)을 쓴다 — 같은 함수를 재시도와 라운드 파생 양쪽에 쓰면 `generateStage(base)`가 내부 재시도로 우연히 `deriveSeed(base)`를 채택했을 때 2R 시드와 정확히 충돌해 1R=2R이 되는 문제가 실측으로 발견됐다. `seedForRound(base, 1) === base`라 기존 `generateStage(DEFAULT_SEED)` 호출부(1R)와 호환된다.
- **라운드-스테이지 재생성 연동**: 한 라운드의 골 도달 시(`isStageCleared`) `core/round.ts`의 `roundAfterClear`로 다음 라운드 여부/전체 클리어 여부를 결정하고, 다음 라운드면 `generateStage(seedForRound(...))`로 완전히 새 스테이지를 생성해 전환한다(`ui/GameCanvas.tsx`의 `loadStage`). 체크포인트(`checkpointPathIndices`)·진척도 리스폰(`respawnIndexFor`) 로직은 폐기하지 않고 "이 라운드 스테이지 내부" 세이브 포인트 용도로 그대로 유지한다 — 라운드 전환(스테이지 교체)과 스테이지 내부 세이브 포인트는 서로 다른 개념으로 명확히 분리했다.
- 부수적으로, 넓은 시드 sweep 테스트 중 체크포인트가 스폰/서로 다른 체크포인트와 좌표가 겹치는 드문 경우(막다른 통로에서 재방문된 셀이 체크포인트 인덱스와 겹침)가 발견되어, `generateStage`의 재시도 게이트에 "스폰/체크포인트/골이 모두 서로 다른 좌표인지" 조건을 추가했다(`hasDistinctCells`).

## 버그 수정 기록 (2026-07-28): 진척도 판정이 유클리드 최근접이라 벽을 무시하던 문제

`core/round.ts`의 `nearestPathIndex`는 캐릭터 위치에서 `stage.path`(carve 순서 통로 중심점)
중 유클리드 거리로 가장 가까운 인덱스를 진척도로 썼다. `carveCorridor`가 좁은 20×15 그리드
안에서 자기 자신 근처를 지나가는 경우가 흔해(300시드 전수 실측), 캐릭터가 통로 초반부에
있어도 벽 하나 너머의 먼 인덱스(체크포인트·골 근처)가 "가장 가깝다"고 오판되는 사례가
프로덕션 시드(`DEFAULT_SEED=12345` 1R 포함, path index 36과 78의 좌표가 완전히 동일했음)에서
실측 확인됐다 — 벽을 뛰어넘어 체크포인트/골을 조기 통과 처리할 수 있는 정확성 버그.

- **수정**: 진척도 판정을 유클리드 최근접 탐색에서, `generateStage` 시점에 스폰 기준으로
  한 번 계산하는 BFS 그래프 거리 필드(`Stage.distanceField`, `procgen/reachability.ts`의
  `bfsDistances`)로 교체했다. 매 프레임은 캐릭터가 서 있는 셀의 값을 O(1) 조회만 한다
  (`core/round.ts`의 `progressAt`). 벽을 넘어가는 경로는 BFS 자체가 만들 수 없으므로, 이
  결함 클래스는 구조적으로 재발 불가능하다.
- **부수 발견**: 통로 폭이 2칸이라 서로 다른 carve 스텝의 셀이 벽 없이 walkable-인접할 수
  있어(진짜 지름길), BFS 거리 기준 체크포인트 진행도가 carve 순서와 다르게 뒤바뀔 수 있음이
  확인됐다(1000시드 sweep 중 재시도 30회로는 36건 실패). `generateStage`의 기존 재시도
  게이트(`hasDistinctCells`와 같은 자리)에 "체크포인트·골 진행도가 오름차순인지"
  (`isAscendingProgress`) 조건을 추가하고, 재시도 예산을 30→200회로 올려(BFS까지 포함해도
  1000시드 생성 486ms — 체감 지연 없음) 1000시드 전부 통과하는 것을 확인 후 반영했다.
- **API 변경**: `nearestPathIndex`/`respawnIndexFor` 폐기, `progressAt`/`respawnPointFor`로
  대체(`Stage`에 `distanceField`/`checkpointProgress`/`goalProgress` 필드 추가). `path`/
  `checkpointPathIndices`는 체크포인트 "배치" 로직(carve 순서 기반 균등 분할)이 계속 필요로
  하므로 그대로 유지했다 — 이번 수정은 "진척도 판정" 축만 교체했고 "체크포인트 배치" 축은
  건드리지 않았다.

## 버그 수정 기록 (2026-08-04): 밟은 적 없는 세이브 포인트가 활성화·리스폰되던 문제

플레이 중 "찍지도 않은 세이브 포인트가 활성 표시되고, 죽으면 처음 보는 지점에서 재개된다"는
제보로 확인된 버그다. 위 2026-07-28 수정이 남겨둔 **"체크포인트 배치" 축**이 원인이었다.

세이브 포인트 활성화 판정이 `farthestProgress >= checkpointProgress[i]`, 즉 **스칼라 값
하나(스폰 기준 BFS 거리) 비교**였다. BFS 거리는 방향 정보가 없어서 "스폰에서 15칸"인 셀이
맵 곳곳에 흩어져 있는데, 판정은 그 크기만 비교하므로 체크포인트와 **정반대 갈래로 진행해도
통과 처리**됐다. 체크포인트 반경 2칸을 통행 금지로 막고 스폰에서 BFS를 돌려 실측한 결과,
전 라운드(1R/2R/3R)의 모든 체크포인트가 "근처에 얼씬도 하지 않고" 골 진행도까지 도달
가능했다 — 6/6 전부 재현.

같은 원인의 2차 증상으로, 체크포인트가 코스 초반에 몰려 있었다. 배치는 `path`(carve 순서)
인덱스 균등 분할인데 판정은 BFS 거리라 **두 척도가 서로 달랐다**. 통로 폭이 2칸이라 서로
다른 carve 구간이 벽 없이 인접·병합되면서, path 상 한참 뒤인 지점도 스폰에서의 실제 통로
거리는 코앞인 경우가 흔하다 — 골 진행도가 22인 1R에서 체크포인트 진행도가 3, 5로 나와
스폰에서 다섯 걸음이면 둘 다 지나쳐진 상태가 됐다.

- **활성화 판정 교체**: 진행도 비교 → **실제 접촉**(`core/round.ts`의 `hasTouchedCheckpoint`,
  반경 `CHECKPOINT_TOUCH_RADIUS = 40px` = 통로 폭 80px의 절반). `ui/GameCanvas.tsx`가 프레임마다
  접촉을 검사해 한 번 닿으면 래치(`checkpointsReachedRef`)하고, 리스폰·화면 표시가 모두 이 값만
  본다. 밟지 않은 지점이 활성화되는 것이 원리적으로 불가능해졌다. `respawnPointFor` 시그니처가
  `(spawn, checkpoints, reached)`로 바뀌었다.
- **배치 기준 교체**: `computeCheckpointCells`가 후보를 **스폰→골 최단 경로 위 셀**
  (`distanceField`를 골에서 역추적)로 제한하고, 그중 **BFS 진행도를 균등 분할한 지점**
  (1개면 정확히 절반)을 고른다. 두 축이 각각 다른 문제를 푼다.
  - *최단 경로 제한* → 길목에 놓기. 후보를 `path`(carve 순서 전체) 위로 두면 세이브 포인트가
    막다른 갈래나 되돌아가는 구간에 놓여, 일부러 찾아가지 않는 한 마주칠 일이 없었다(실측:
    2R·3R의 최단 경로가 체크포인트를 지나지 않음, 2R은 맵 구석 (20,60)에 배치됨).
  - *진행도 균등 분할* → 코스 중간에 놓기. 1~200 시드 실측에서 배치 진행도 비율이 전부 정확히
    50%로 수렴 — 회귀 방지 테스트로 30~70% 구간을 고정했다.

  배치 결과 실측(1~100 시드): 체크포인트를 밟기 위해 더 걸어야 하는 거리가 **중앙값 -5px,
  최대 30px**(캐릭터 속도 220px/초 기준 0.14초)로 사실상 공짜이고, 동시에 100/100 시드에서
  우회도 가능하다 — 밟을지 말지가 실제 선택으로 남는다. "체크포인트가 최단 경로 위에 있다"는
  조건은 구현 함수를 재사용하지 않고 `스폰→CP 거리 + CP→골 거리 == 스폰→골 거리`라는 최단
  경로의 정의로 1~200 시드 전수 검증한다.
- **개수 조정**: `SAVE_POINTS_PER_STAGE` 2 → **1**(라운드당 코스 중간 한 곳). 2개일 때는 간격이
  촘촘해 사망 페널티가 사실상 사라졌다.
- **의도된 사양 확인**: 세이브 포인트를 밟을지는 플레이어 선택이며, 하나도 밟지 않고 골까지
  클리어하는 것도 정상이다(그 경우 사망 시 항상 스폰으로 복귀). 캐릭터 충돌 반경을 반영한
  픽셀 단위 우회 경로 탐색으로 1~30 시드 전부에서 우회 가능함을 실측 확인했다.
- **폐기**: `computeCheckpoints`(테스트 전용 헬퍼, `generateStage`와 중복이라 제거),
  `Stage.checkpointPathIndices`(체크포인트가 `path` 인덱스가 아니라 최단 경로 위 셀로
  결정되므로 표현할 수 없고, 쓰는 곳도 없어졌다). `checkpointProgress`는 남지만 용도가
  런타임 판정 → **배치 검증 전용**으로 축소됐다. `Stage.path`는 광원(가로등) 배치 기준으로만
  쓰인다.

## 버그 수정 기록 (2026-08-05): 골에 도달하지 않았는데 클리어 판정되던 문제

플레이 중 "골 근처에도 못 갔는데 클리어됐다"는 제보로 확인된 버그다. 바로 위 2026-08-04
수정이 세이브 포인트에 대해서만 고치고 **골 자체**에는 남겨둔 같은 원인이었다 — 골 도달
판정(`isStageCleared`)이 여전히 `farthestProgress >= goalProgress`, 즉 스칼라 BFS 거리
비교였다. 통로 폭 2칸(`CORRIDOR_WIDTH`)이 만드는 막다른 갈래가 골보다 더 큰 BFS 거리를
가지면, 골 쪽으로는 가지도 않고 그 갈래에 발을 들이기만 해도 "진척도가 골 진척도를
넘었다"고 오판해 클리어 처리됐다.

- **판정 교체**: 진행도 비교 → 세이브 포인트와 동일하게 **실제 접촉**
  (`core/round.ts`의 `hasTouchedCheckpoint`를 `stage.goal`에 재사용, 반경 40px). 골에
  물리적으로 닿아야만 클리어된다.
- **폐기**: 런타임에서만 쓰이던 `progressAt`·`isStageCleared`(`core/round.ts`)와
  `farthestProgressRef`(`ui/GameCanvas.tsx`)를 제거했다. `Stage.goalProgress`는 스테이지
  생성 시 체크포인트 배치·오름차순 검증(`isAscendingProgress`)에는 계속 쓰이므로 남긴다 —
  용도가 런타임 클리어 판정 → **배치 검증 전용**으로 축소된 것은 `checkpointProgress`가
  겪은 것과 같은 궤적이다.
